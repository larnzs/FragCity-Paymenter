# FragCityAPI — Paymenter Bridge

Compatibility target: Paymenter **v1.5.9**. Bridge contract version: **1.12.0**. This is a separate Paymenter add-on. It does not modify Paymenter Core and does not replace the FragCity CS2 server extension.

## Purpose

Provides a narrow private server-to-server bridge for FragCity identity, paid CS2 orders and customer server access:

- `POST /api/v1/fragcity/bridge/ping`
- `POST /api/v1/fragcity/bridge/catalog/cs2`
- `POST /api/v1/fragcity/bridge/wallet/balance`
- `POST /api/v1/fragcity/bridge/wallet/topups/prepare`
- `POST /api/v1/fragcity/bridge/wallet/topups/zarinpal`
- `POST /api/v1/fragcity/bridge/users/sync`
- `POST /api/v1/fragcity/bridge/quotes/cs2`
- `POST /api/v1/fragcity/bridge/orders/cs2`
- `POST /api/v1/fragcity/bridge/servers/list`
- `POST /api/v1/fragcity/bridge/servers/password`
- `POST /api/v1/fragcity/bridge/servers/username`

All bridge routes require an HMAC-SHA256 signature, a timestamp within five minutes, a unique nonce and HTTPS. They are server-to-server endpoints; the browser must never call them directly.

## Configuration

After installing and enabling the extension under **Admin → Extensions → Others**, configure:

- `shared_secret`: 64+ hexadecimal characters generated by `openssl rand -hex 32`. Configure the same value in FragCity's private runtime `settings/settings.json` under `integrations.paymenter_backend.shared_secret`.
- `allowed_ips`: optional exact source-IP allowlist, comma- or newline-separated. Use the shared host's stable outbound IP when available.

Keep the secret out of Git, browser code and logs.

## User synchronization

Request body:

```json
{
  "steamid64": "7656119XXXXXXXXXX",
  "username": "fragcity_user1",
  "email": "customer@example.com",
  "phone": "09123456789",
  "first_name": "Customer",
  "last_name": "Example",
  "password": "customer-supplied-password"
}
```

The example values are placeholders. `username` is mandatory, lowercased, 3–50 characters, starts and ends with an ASCII letter or digit, and allows only ASCII letters, digits, underscores and hyphens. It is stored as the Paymenter user property `fragcity_username` because Paymenter has no native username field. The dedicated FragCity CS2 server extension reads that property and creates/updates the Pterodactyl client using its native `username` field. Both `first_name` and `last_name` are mandatory, non-empty after trimming, and limited to 191 characters. They are written to Paymenter's native User fields. Password is accepted only over HTTPS inside the signed server-to-server request. It is never returned, logged or persisted as plaintext. Paymenter's User model hashes the password.

The mapping table `fragcity_user_links` enforces a unique Paymenter user per FragCity SteamID and a unique FragCity SteamID per Paymenter user. The FragCity username, phone and SteamID are stored as Paymenter user properties. The endpoint is idempotent for a linked SteamID.

An existing Paymenter account with the same email is linked only when its current password matches the supplied password and it is not already linked to another SteamID. Otherwise the endpoint returns HTTP 409; it never silently claims an unrelated account by email alone.

FragCity is the identity source of truth. A successful authenticated sync refreshes Paymenter's email, name and password to match the current FragCity account. Do not let customers change credentials directly in Paymenter; credential changes should originate in FragCity and be synchronized.

## Customer server inventory and panel password

FragCity requests the customer's services by the authenticated SteamID64. The bridge resolves that SteamID64 through `fragcity_user_links`, lists only non-cancelled services owned by the linked Paymenter user, and exposes only products assigned to the `FragCityCS2` server extension. Each returned service summary also includes the IDs of its own `ServiceUpgrade` records (`service_upgrade_ids`), allowing invoice upgrade lines to be matched to their parent service without guessing.

The server extension returns an allow-listed summary from the Pterodactyl Application API: service ID/status, server UUID/identifier/name, node ID, resource limits, dates, panel URL, panel username and email. Server ownership is verified by both the Pterodactyl `external_id` (Paymenter service ID) and Pterodactyl owner user ID before data is returned.

The inventory read also repairs a legacy Pterodactyl client identity when its email matches the linked Paymenter account and its `external_id` is empty or already matches that Paymenter user ID. It synchronizes the native Pterodactyl username, email, first/last name and `external_id`; a conflicting external ID or a username collision fails closed.

The `servers/password` endpoint accepts a customer-selected Pterodactyl password only after the signed request is validated and the service is confirmed to belong to the linked Paymenter user. The server extension verifies the Pterodactyl server owner and updates only that user's password through the Pterodactyl Application API. Pterodactyl hashes the password. The bridge stores only a `fragcity_panel_password_set_at` timestamp property; it never stores or returns plaintext or a password hash.

FragCity's website endpoint additionally requires an authenticated website session, CSRF token and successful re-entry of the current FragCity password. The website sends the new panel password to Paymenter only over the signed HTTPS bridge. Never expose the HMAC secret or Pterodactyl Application API key to browser JavaScript.

The panel password is intentionally independent from FragCity and Paymenter passwords. It cannot be read back after setting; customers can set a new one through FragCity at any time.

## CS2 catalogue and wallet balance

The website backend reads the configured CS2 catalogue through
`POST /api/v1/fragcity/bridge/catalog/cs2`. The response includes the configured
Product, the four configured duration Plans, their Rial prices, every visible
Product Config Option, all child values and each child price by supported
billing duration, plus the Egg Checkout fields and GameModeManager compatibility
manifest. Config Option child prices are resolved exactly like Paymenter's
native CartItem calculation: by billing period/unit and currency, not by
reusing the Product Plan ID. Missing child prices are explicitly marked
unavailable. The response is intended for the private PHP backend; never expose
the HMAC secret or let browser JavaScript call Paymenter directly.

The website backend reads a linked customer's Rial wallet through
`POST /api/v1/fragcity/bridge/wallet/balance` with only the SteamID64 from the
authenticated FragCity server-side session. Paymenter resolves the linked User
from `fragcity_user_links` and returns only the configured currency balance plus whether Credits are enabled and the configured minimum deposit, maximum deposit and maximum balance.
An unknown or unlinked SteamID fails closed.

Before FragCity creates an external ZarinPal wallet-deposit request, it must call
`POST /api/v1/fragcity/bridge/wallet/topups/prepare`. Paymenter validates the
native Credits settings (enabled, minimum deposit, maximum deposit and maximum
balance), rejects an existing pending Credit invoice and reserves the user's
remaining maximum-credit capacity for 20 minutes. The reservation is keyed by
a stable `topup_ref`; exact retries return the same reservation and conflicting
payloads are rejected.

Only after receiving a `prepared` response should FragCity create the
ZarinPal payment request. After the website verifies the callback with
ZarinPal's server-side Verify API, it settles the same reservation through
`POST /api/v1/fragcity/bridge/wallet/topups/zarinpal`. Paymenter enforces the
Rial/Toman conversion and unique `topup_ref`, Authority and RefID. It creates
a native Invoice with a Credit InvoiceItem, records a successful external
Paymenter InvoiceTransaction, and marks the invoice paid. Paymenter's native
`ProcessPaidInvoiceService` then increments the customer's Credit row after
the database commit. The same verified receipt cannot be reused for a CS2
purchase or another top-up because both flows share
`fragcity_payment_receipts`.

Reservations normally expire after 20 minutes. If a customer has already
completed a real payment but the callback arrives after expiry, the verified
payment is still reconciled rather than discarded; this exceptional late
settlement can outlive the reservation's maximum-credit estimate.

For this flow, configure **Settings → Credits** in Paymenter: enable Credits
and set the minimum deposit, maximum deposit and maximum credit in the configured
Rial currency's units. The extension fails closed when Credits are disabled or
those limits are not configured.

## Authoritative CS2 checkout quotes

The FragCity backend calls `POST /api/v1/fragcity/bridge/quotes/cs2` before
creating a ZarinPal payment request. The request contains the linked SteamID64,
duration, server name, resource selections, feature limits and allow-listed Egg
selections. The quote endpoint is read-only: it never creates an invoice, order,
service or wallet transaction.

Paymenter resolves the configured Product and duration Plan, resolves all eight
native Config Option child values, loads the linked Paymenter User, and applies
`Settings::tax($user)` to the same Plan + recurring Config Option prices + setup
fees used by the paid-order endpoint. It returns an exact Rial total and its
whole-Toman equivalent only when the total is representable in whole Toman.
It does not accept any price, tax amount, Plan ID, Product ID or Config Option ID
from FragCity.

The quote is a short-lived display/confirmation value, not a payment token.
When the paid order is submitted, `orders/cs2` independently reloads the current
Plan and Config Option prices and recalculates tax. A ZarinPal receipt must match
that new total exactly; a price or tax change between quote and payment therefore
fails closed instead of silently charging a different amount. Wallet purchases
continue to be priced and debited atomically by Paymenter.
## Paid CS2 server orders

`POST /api/v1/fragcity/bridge/orders/cs2` accepts a server-to-server order using either a verified ZarinPal receipt or the linked customer's Paymenter Wallet. For ZarinPal, FragCity must first verify the payment with ZarinPal's Verify API; Paymenter does **not** trust a browser redirect, a browser-supplied `Status=OK`, or a client-provided payment claim. For Wallet, the request contains only `payment.provider=wallet`; Paymenter computes the amount and locks/debits its own Credit row. The HMAC-authenticated website backend is the only caller.

After validation, the endpoint creates native Paymenter records:
- an `Order`;
- a pending `Service` assigned to the configured FragCity CS2 Product and duration Plan;
- service properties for `servername` and the six remaining Egg variables. `SRCDS_MAXPLAYERS` and `TICKRATE` are not duplicated as service properties;
- native Paymenter `ServiceConfig` rows for eight Product Config Options: RAM, SSD, CPU, Player Slots, Tickrate, Databases, Additional Allocations and Backups. The bridge resolves each submitted value to exactly one child under the matching parent option, then requires a price row for the selected Plan and Rial currency. These `ServiceConfig` rows are the persisted source of truth. Paymenter's `ExtensionHelper::getServiceProperties()` adds the selected child Environment Variables to the provisioning property map; `FragCityCS2` adapts RAM/SSD/CPU to Pterodactyl resource limits, passes Player Slots/Tickrate to Egg environment values, and maps the three feature-limit selections to Pterodactyl's `feature_limits.databases`, `feature_limits.allocations` and `feature_limits.backups`. Missing/ambiguous mappings, unsupported values or missing recurring option prices fail closed before an order is accepted;
- an invoice item linked to that service;
- for ZarinPal, a successful external Paymenter invoice transaction containing the ZarinPal reference plus a global receipt-ledger entry;
- for Wallet, an atomic Paymenter Credit debit and a successful invoice transaction marked as a credit transaction (no external payment reference).

The endpoint then marks the invoice paid. Paymenter's native `InvoiceObserver` and `ProcessPaidInvoiceService` run after the database commit; Paymenter dispatches its normal `CreateJob`, and `FragCityCS2` delegates provisioning to Paymenter's inherited Pterodactyl extension. This endpoint does not call Pterodactyl directly.

### Required API extension settings

Configure these under **Paymenter Admin → Extensions → Others → FragCity API** after updating the extension:

| Setting | Meaning |
| --- | --- |
| `cs2_product_id` | Product ID whose Server Extension is `FragCityCS2` |
| `cs2_plan_id_1_day` | Product Plan for exactly 3 days (legacy setting key retained for compatibility) |
| `cs2_plan_id_7_days` | Product Plan for exactly 1 week |
| `cs2_plan_id_15_days` | Product Plan for exactly 15 days |
| `cs2_plan_id_30_days` | Product Plan for exactly 1 month |
| `cs2_currency_code` | Existing Paymenter Rial currency code used by all four Plans (for example `IRR`) |

Each Plan ID must belong to the configured Product, be recurring, and have a price row for the configured Rial currency. Billing periods are checked: 3 days = `3 days`, 7 days = `1 week`, 15 days = `15 days`, and 30 days = `1 month`. Every selected RAM, disk, CPU, Player Slots, Tickrate, Databases, Additional Allocations and Backups child must also have a price row for the selected Plan and Rial currency. The Player Slots 5-child and every Tickrate/feature-limit child must have zero-price rows; Player Slots above the included capacity use the configured capacity surcharge. The API fails closed when the Product, Plan, currency, option mapping, supported value or child price is missing or inconsistent.

### Required Product Config Options

Attach all eight Config Options to the configured CS2 Product. The parent Environment Variable must match exactly:

| Config Option | Parent Environment Variable | Type | Child Environment Variables |
| --- | --- | --- | --- |
| RAM | `memory_mb` | Select | `1024`, `1280`, `1536` |
| SSD Storage | `disk_mb` | Select | `5120`, `6144`, `7168`, `8192`, `9216`, `10240` |
| CPU | `cpu_percent` | Select | `100`, `200`, `300`, `400` |
| Player Slots | `SRCDS_MAXPLAYERS` | Select | Every integer from `5` through `64` |
| Tickrate | `TICKRATE` | Select | `64`, `128` |
| Databases | `databases` | Select | `0`, `1`, `2`, `3`, `5`, `10` |
| Additional Allocations | `additional_allocations` | Select | `0`, `1`, `2`, `3`, `5` |
| Backups | `backups` | Select | `0`, `1`, `2`, `3`, `5`, `10` |

Use exact numeric child Environment Variables, not display labels. **Enable `Upgradable` for all eight Config Options.** Paymenter 1.5.9 replaces a service's Config rows with the selections submitted by its native Service Upgrade flow; non-upgradable options are omitted and can be deleted. FragCityCS2 now resolves all eight native selections again during both initial provisioning and upgrades. Each child must have a price row for every supported Plan/currency. For Player Slots, the 5-slot child is the included/base capacity and larger values represent the additional-slot surcharge. Both Tickrate children and every Databases/Additional Allocations/Backups child must remain zero-price and zero-setup-fee until the storefront quote supports those surcharges. Paymenter calculates any paid option changes through its native upgrade billing. The Egg Startup command passes the selected Tickrate through `-tickrate {{TICKRATE}}`. The three feature-limit options are not Egg variables: `FragCityCS2` maps them directly to Pterodactyl's server feature limits.

**Currency is Rial-only inside Paymenter.** The bridge recalculates the invoice amount inside Paymenter from the configured Product Plan plus every selected Config Option Child price for the chosen billing period/unit and Rial currency. It includes setup fees and the applicable Paymenter customer tax policy using the same pricing model as the native Paymenter cart. The amount sent by FragCity is only accepted when it exactly matches this independently calculated total and is representable in whole Toman (10 Rial per Toman). The bridge then creates the Paymenter Service, Invoice Item and successful Invoice Transaction using the recalculated Rial total; it never trusts a browser-supplied price or uses Toman as a Paymenter monetary amount.

### Signed request body

The HMAC signature covers the exact raw JSON request body. The website sends the verified payment receipt together with the configuration snapshot:

```json
{
  "order_ref": "32-character-unique-hex-reference",
  "steamid64": "7656119XXXXXXXXXX",
  "payment": {
    "provider": "zarinpal",
    "authority": "ZarinPal authority",
    "ref_id": "ZarinPal verified reference",
    "amount_toman": 749000,
    "amount_rial": 7490000
  },
  "duration_days": 30,
  "server_name": "FragCity Public",
  "resources": {
    "memory_mb": 1024,
    "disk_mb": 10240,
    "cpu_percent": 100
  },
  "feature_limits": {
    "databases": 0,
    "additional_allocations": 0,
    "backups": 0
  },
  "egg": {
    "SRCDS_MAP": "de_dust2",
    "SRCDS_MAXPLAYERS": "10",
    "TICKRATE": "64",
    "EXEC": "comp.cfg",
    "MAPGROUP": "mg_comp",
    "COOLDOWN": "0",
    "ENABLE_GUARD": "0",
    "GUARD_BAN_MINUTES": "60"
  }
}
```

The example is illustrative; the amount, reference and identity must come from the website's server-side order record and verified ZarinPal response. The two amounts must match exactly at the 10 Rial per Toman conversion. `order_ref` must be generated once by FragCity and reused unchanged for retries.

The signed `resources` object is a selection snapshot, not an allowlist or price source. The bridge validates safe numeric bounds, then requires each submitted RAM, SSD and CPU amount to match exactly one Child Environment Variable under the corresponding Config Option attached to the configured Product. Therefore the actual options and their allowed values come from Paymenter's current Product configuration, not a hard-coded list in the website or bridge. The Egg values are separately validated against the live `FragCityCS2` Checkout manifest, including allowed select values. UI labels are never stored as Egg values.

### Idempotency and paid add-ons

- Databases, Additional Allocations and Backups are included/free for now. Every selected child must have a zero-price and zero-setup-fee row for the chosen Plan and Rial currency.

- `order_ref` is unique. ZarinPal Authority and verified RefID are stored in the shared `fragcity_payment_receipts` ledger, which is also used by wallet top-ups; the unique constraints prevent cross-purpose receipt reuse.
- An exact retry with the same order reference and payload hash returns the existing Paymenter Order, Invoice and Service IDs; it never creates a second service or debits Wallet twice.
- Reusing an order reference with a different payload, or attempting to spend an already-used ZarinPal receipt, returns a conflict. Wallet checkout locks the linked Paymenter Credit row and fails without creating records when the available balance is insufficient.
- The accepted response means the Paymenter Order/Invoice/Service records were committed and the native provisioning flow was queued. It does not claim that Pterodactyl has already finished creating the server.
- `TICKRATE=64` and `TICKRATE=128` are both accepted as free native Config Option values. `ENABLE_GUARD=1` remains blocked until its paid surcharge is included in the authoritative storefront quote.

**Renewals still require an end-to-end pricing test:** RAM/CPU/SSD, Player Slots, Tickrate, Databases, Additional Allocations and Backups are native recurring Config Options, and the bridge verifies that each selected value has a price for the configured Plan and currency. Before enabling automatic renewal billing, verify that Paymenter's recurring total (Plan plus Config Option prices and any other paid add-ons such as slots) exactly matches FragCity's storefront quote and does not double-charge or omit any component. `ENABLE_GUARD=1` remains blocked until its surcharge is implemented in the authoritative storefront quote.

## Installation

Copy this directory to:

```text
extensions/Others/FragCityAPI/
```

Then rebuild Composer's classmap and clear Laravel caches:

```bash
cd /var/www/paymenter
composer dump-autoload
php artisan optimize:clear
```

Enable **FragCity API** in Paymenter Admin → Extensions → Others and configure the secret. The extension migration runs when it is installed. Do not uninstall the extension after creating user links unless the mapping table has been backed up.

## Security notes

- HMAC message: `timestamp + newline + nonce + newline + raw request body`.
- Headers: `X-FragCity-Timestamp`, `X-FragCity-Nonce`, `X-FragCity-Signature`.
- Nonces are stored atomically in Laravel Cache for ten minutes to prevent replay.
- Request bodies and passwords are never written to logs.
- Core API keys and Pterodactyl credentials are not used by this bridge.
- The bridge creates no Pterodactyl users or servers; the FragCity CS2 server extension handles Pterodactyl client identity immediately before the official Paymenter server provisioner runs.

## Customer panel username

The `servers/username` endpoint updates the customer's Pterodactyl Client username for one owned CS2 service. The signed bridge resolves the SteamID64 to the linked Paymenter user, verifies service ownership, and delegates the operation to FragCityCS2. The website must authenticate the customer and protect the request with CSRF before sending it through the private HTTPS HMAC bridge.
