# FragCityAPI — Paymenter Bridge

Compatibility target: Paymenter **v1.5.9**. Bridge contract version: **1.5.1**. This is a separate Paymenter add-on. It does not modify Paymenter Core and does not replace the FragCity CS2 server extension.

## Purpose

Provides a narrow private server-to-server bridge for FragCity identity, paid CS2 orders and customer server access:

- `POST /api/v1/fragcity/bridge/ping`
- `POST /api/v1/fragcity/bridge/users/sync`
- `POST /api/v1/fragcity/bridge/orders/cs2`
- `POST /api/v1/fragcity/bridge/servers/list`
- `POST /api/v1/fragcity/bridge/servers/password`
- `POST /api/v1/fragcity/bridge/servers/username`

All bridge routes require an HMAC-SHA256 signature, a timestamp within five minutes, a unique nonce and HTTPS. They are server-to-server endpoints; the browser must never call them directly.

## Configuration

After installing and enabling the extension under **Admin → Extensions → Others**, configure:

- `shared_secret`: 64+ hexadecimal characters generated by `openssl rand -hex 32`. Configure the same value in FragCity's private runtime `settings/settings.json` under `integrations.paymenter_backend.shared_secret`.
- `allowed_ips`: optional exact source-IP allowlist, comma- or newline-separated. Use the shared host's stable outbound IP when available.

Keep the secret out of Git, browser code and logs.

## User synchronization

Request body:

```json
{
  "steamid64": "7656119XXXXXXXXXX",
  "username": "fragcity_user1",
  "email": "customer@example.com",
  "phone": "09123456789",
  "first_name": "Customer",
  "last_name": "Example",
  "password": "customer-supplied-password"
}
```

The example values are placeholders. `username` is mandatory, lowercased, 3–50 characters, starts and ends with an ASCII letter or digit, and allows only ASCII letters, digits, underscores and hyphens. It is stored as the Paymenter user property `fragcity_username` because Paymenter has no native username field. The dedicated FragCity CS2 server extension reads that property and creates/updates the Pterodactyl client using its native `username` field. Both `first_name` and `last_name` are mandatory, non-empty after trimming, and limited to 191 characters. They are written to Paymenter's native User fields. Password is accepted only over HTTPS inside the signed server-to-server request. It is never returned, logged or persisted as plaintext. Paymenter's User model hashes the password.

The mapping table `fragcity_user_links` enforces a unique Paymenter user per FragCity SteamID and a unique FragCity SteamID per Paymenter user. The FragCity username, phone and SteamID are stored as Paymenter user properties. The endpoint is idempotent for a linked SteamID.

An existing Paymenter account with the same email is linked only when its current password matches the supplied password and it is not already linked to another SteamID. Otherwise the endpoint returns HTTP 409; it never silently claims an unrelated account by email alone.

FragCity is the identity source of truth. A successful authenticated sync refreshes Paymenter's email, name and password to match the current FragCity account. Do not let customers change credentials directly in Paymenter; credential changes should originate in FragCity and be synchronized.

## Customer server inventory and panel password

FragCity requests the customer's services by the authenticated SteamID64. The bridge resolves that SteamID64 through `fragcity_user_links`, lists only non-cancelled services owned by the linked Paymenter user, and exposes only products assigned to the `FragCityCS2` server extension. Each returned service summary also includes the IDs of its own `ServiceUpgrade` records (`service_upgrade_ids`), allowing invoice upgrade lines to be matched to their parent service without guessing.

The server extension returns an allow-listed summary from the Pterodactyl Application API: service ID/status, server UUID/identifier/name, node ID, resource limits, dates, panel URL, panel username and email. Server ownership is verified by both the Pterodactyl `external_id` (Paymenter service ID) and Pterodactyl owner user ID before data is returned.

The inventory read also repairs a legacy Pterodactyl client identity when its email matches the linked Paymenter account and its `external_id` is empty or already matches that Paymenter user ID. It synchronizes the native Pterodactyl username, email, first/last name and `external_id`; a conflicting external ID or a username collision fails closed.

The `servers/password` endpoint accepts a customer-selected Pterodactyl password only after the signed request is validated and the service is confirmed to belong to the linked Paymenter user. The server extension verifies the Pterodactyl server owner and updates only that user's password through the Pterodactyl Application API. Pterodactyl hashes the password. The bridge stores only a `fragcity_panel_password_set_at` timestamp property; it never stores or returns plaintext or a password hash.

FragCity's website endpoint additionally requires an authenticated website session, CSRF token and successful re-entry of the current FragCity password. The website sends the new panel password to Paymenter only over the signed HTTPS bridge. Never expose the HMAC secret or Pterodactyl Application API key to browser JavaScript.

The panel password is intentionally independent from FragCity and Paymenter passwords. It cannot be read back after setting; customers can set a new one through FragCity at any time.

## Paid CS2 server orders

`POST /api/v1/fragcity/bridge/orders/cs2` accepts a server-to-server order only after the FragCity website has verified the ZarinPal payment with ZarinPal's Verify API. Paymenter does **not** trust a browser redirect, a browser-supplied `Status=OK`, or a client-provided claim that a payment succeeded. The HMAC-authenticated website backend is the only caller.

After validation, the endpoint creates native Paymenter records:
- an `Order`;
- a pending `Service` assigned to the configured FragCity CS2 Product and duration Plan;
- service properties for `servername` and the eight approved CS2 Egg Checkout variables only;
- native Paymenter `ServiceConfig` rows for the selected RAM, SSD and CPU Config Options. The bridge resolves each selected resource amount to exactly one Product option child by its `Environment Variable`, then requires a price for the selected Plan and currency. These `ServiceConfig` rows are the sole persisted source of truth for RAM/SSD/CPU; `FragCityCS2` maps them to the inherited Pterodactyl `memory`, `disk` and `cpu` inputs immediately before server creation or resource upgrade. The bridge does not duplicate them as service properties. Missing or ambiguous mappings, or missing recurring option prices, fail closed before an order is accepted;
- an invoice item linked to that service;
- a successful Paymenter invoice transaction containing the ZarinPal reference.

The endpoint then marks the invoice paid. Paymenter's native `InvoiceObserver` and `ProcessPaidInvoiceService` run after the database commit; Paymenter dispatches its normal `CreateJob`, and `FragCityCS2` delegates provisioning to Paymenter's inherited Pterodactyl extension. This endpoint does not call Pterodactyl directly.

### Required API extension settings

Configure these under **Paymenter Admin → Extensions → Others → FragCity API** after updating the extension:

| Setting | Meaning |
| --- | --- |
| `cs2_product_id` | Product ID whose Server Extension is `FragCityCS2` |
| `cs2_plan_id_1_day` | Product Plan for exactly 1 day |
| `cs2_plan_id_7_days` | Product Plan for exactly 1 week |
| `cs2_plan_id_15_days` | Product Plan for exactly 15 days |
| `cs2_plan_id_30_days` | Product Plan for exactly 1 month |
| `cs2_currency_code` | Existing Paymenter Rial currency code used by all four Plans (for example `IRR`) |

Each Plan ID must belong to the configured Product, be recurring, and have a price row for the configured Rial currency. Billing periods are checked: 1 day = `1 day`, 7 days = `1 week`, 15 days = `15 days`, and 30 days = `1 month`. The selected RAM, disk and CPU Config Option values must also each have a price row for the selected Plan and Rial currency. The API fails closed when the product, plans, currency or mappings are missing or inconsistent.

**Currency is Rial-only inside Paymenter.** The bridge always creates the Paymenter Service, Invoice item and successful Invoice Transaction using `payment.amount_rial`. `payment.amount_toman` remains the source amount used for the conversion-integrity check and order audit. The bridge verifies `amount_rial === amount_toman * 10`; it never uses the Toman amount for Paymenter monetary records.

### Signed request body

The HMAC signature covers the exact raw JSON request body. The website sends the verified payment receipt together with the configuration snapshot:

```json
{
  "order_ref": "32-character-unique-hex-reference",
  "steamid64": "7656119XXXXXXXXXX",
  "payment": {
    "provider": "zarinpal",
    "authority": "ZarinPal authority",
    "ref_id": "ZarinPal verified reference",
    "amount_toman": 749000,
    "amount_rial": 7490000
  },
  "duration_days": 30,
  "server_name": "FragCity Public",
  "resources": {
    "memory_mb": 1024,
    "disk_mb": 10240,
    "cpu_percent": 100
  },
  "egg": {
    "SRCDS_MAP": "de_dust2",
    "SRCDS_MAXPLAYERS": "10",
    "TICKRATE": "64",
    "EXEC": "comp.cfg",
    "MAPGROUP": "mg_comp",
    "COOLDOWN": "0",
    "ENABLE_GUARD": "0",
    "GUARD_BAN_MINUTES": "60"
  }
}
```

The example is illustrative; the amount, reference and identity must come from the website's server-side order record and verified ZarinPal response. The two amounts must match exactly at the 10 Rial per Toman conversion. `order_ref` must be generated once by FragCity and reused unchanged for retries.

Resource constraints currently mirror the FragCity storefront: RAM 1024/1280/1536 MB, disk 5120–10240 MB in 1024 MB increments, and CPU 100/200/300/400 percent. The signed `resources` object is still sent by the website as the customer's selection snapshot so the bridge can resolve the exact matching Config Option children; it is not used to create `memory`, `disk` or `cpu` service properties. The selected Config Option children must have numeric `env_variable` values matching those amounts and a price for the selected Plan/currency. The Egg values are validated against the live `FragCityCS2` Checkout manifest, including the allowed select values. UI labels are never stored as Egg values.

### Idempotency and paid add-ons

- `order_ref`, ZarinPal Authority and verified ZarinPal Ref ID have unique database constraints.
- An exact retry with the same order reference and payload hash returns the existing Paymenter Order, Invoice and Service IDs; it never creates a second service.
- Reusing an order reference with a different payload, or attempting to spend an already-used ZarinPal receipt, returns a conflict.
- The accepted response means the Paymenter Order/Invoice/Service records were committed and the native provisioning flow was queued. It does not claim that Pterodactyl has already finished creating the server.
- `TICKRATE=128` and `ENABLE_GUARD=1` are rejected for now because their paid surcharges are declared in the FragCity pricing contract but are not yet incorporated into the live storefront quote. They must not be provisioned as free options.

**Renewals still require an end-to-end pricing test:** RAM/CPU/SSD selections are now native recurring Config Options, and the bridge verifies that each selected value has a price for the configured Plan and currency. Before enabling automatic renewal billing, verify that Paymenter's recurring total (Plan plus Config Option prices and any other paid add-ons such as slots) exactly matches FragCity's storefront quote and does not double-charge or omit any component. `TICKRATE=128` and `ENABLE_GUARD=1` remain blocked until their surcharges are implemented in the authoritative storefront quote.

## Installation

Copy this directory to:

```text
extensions/Others/FragCityAPI/
```

Then rebuild Composer's classmap and clear Laravel caches:

```bash
cd /var/www/paymenter
composer dump-autoload
php artisan optimize:clear
```

Enable **FragCity API** in Paymenter Admin → Extensions → Others and configure the secret. The extension migration runs when it is installed. Do not uninstall the extension after creating user links unless the mapping table has been backed up.

## Security notes

- HMAC message: `timestamp + newline + nonce + newline + raw request body`.
- Headers: `X-FragCity-Timestamp`, `X-FragCity-Nonce`, `X-FragCity-Signature`.
- Nonces are stored atomically in Laravel Cache for ten minutes to prevent replay.
- Request bodies and passwords are never written to logs.
- Core API keys and Pterodactyl credentials are not used by this bridge.
- The bridge creates no Pterodactyl users or servers; the FragCity CS2 server extension handles Pterodactyl client identity immediately before the official Paymenter server provisioner runs.

## Customer panel username

The `servers/username` endpoint updates the customer's Pterodactyl Client username for one owned CS2 service. The signed bridge resolves the SteamID64 to the linked Paymenter user, verifies service ownership, and delegates the operation to FragCityCS2. The website must authenticate the customer and protect the request with CSRF before sending it through the private HTTPS HMAC bridge.
