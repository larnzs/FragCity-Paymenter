# FragCityAPI — Paymenter Bridge

Compatibility target: Paymenter **v1.5.9**. Bridge contract version: **1.6.0**. This is a separate Paymenter add-on. It does not modify Paymenter Core and does not replace the FragCity CS2 server extension.

## Purpose

Provides a narrow private bridge for FragCity identity, native Paymenter Checkout SSO and customer server access:

- `POST /api/v1/fragcity/bridge/ping`
- `POST /api/v1/fragcity/bridge/users/sync`
- `POST /api/v1/fragcity/bridge/checkout-url`
- `GET /extensions/fragcity-api/checkout-login/{token}` (single-use, short-lived SSO token)
- `POST /api/v1/fragcity/bridge/servers/list`
- `POST /api/v1/fragcity/bridge/servers/password`
- `POST /api/v1/fragcity/bridge/servers/username`

All bridge routes require an HMAC-SHA256 signature, a timestamp within five minutes, a unique nonce and HTTPS. They are server-to-server endpoints; the browser must never call them directly.

## Configuration

After installing and enabling the extension under **Admin → Extensions → Others**, configure:

- `shared_secret`: 64+ hexadecimal characters generated by `openssl rand -hex 32`. Configure the same value in FragCity's private runtime `settings/settings.json` under `integrations.paymenter_backend.shared_secret`.
- `allowed_ips`: optional exact source-IP allowlist, comma- or newline-separated. Use the shared host's stable outbound IP when available.

Also configure:

- `cs2_product_id`: the enabled Paymenter Product ID assigned to the `FragCityCS2` server extension. The Product's own Plans and Config Options are used directly; no Plan IDs, resource price maps or Egg Config Option mappings are configured in this API extension.

Keep the secret out of Git, browser code and logs.

## User synchronization

Request body:

```json
{
  "steamid64": "7656119XXXXXXXXXX",
  "username": "fragcity_user1",
  "email": "customer@example.com",
  "phone": "09123456789",
  "first_name": "Customer",
  "last_name": "Example",
  "password": "customer-supplied-password"
}
```

The example values are placeholders. `username` is mandatory, lowercased, 3–50 characters, starts and ends with an ASCII letter or digit, and allows only ASCII letters, digits, underscores and hyphens. It is stored as the Paymenter user property `fragcity_username` because Paymenter has no native username field. The dedicated FragCity CS2 server extension reads that property and creates/updates the Pterodactyl client using its native `username` field. Both `first_name` and `last_name` are mandatory, non-empty after trimming, and limited to 191 characters. They are written to Paymenter's native User fields. Password is accepted only over HTTPS inside the signed server-to-server request. It is never returned, logged or persisted as plaintext. Paymenter's User model hashes the password.

The mapping table `fragcity_user_links` enforces a unique Paymenter user per FragCity SteamID and a unique FragCity SteamID per Paymenter user. The FragCity username, phone and SteamID are stored as Paymenter user properties. The endpoint is idempotent for a linked SteamID.

An existing Paymenter account with the same email is linked only when its current password matches the supplied password and it is not already linked to another SteamID. Otherwise the endpoint returns HTTP 409; it never silently claims an unrelated account by email alone.

FragCity is the identity source of truth. A successful authenticated sync refreshes Paymenter's email, name and password to match the current FragCity account. Do not let customers change credentials directly in Paymenter; credential changes should originate in FragCity and be synchronized.

## Customer server inventory and panel password

FragCity requests the customer's services by the authenticated SteamID64. The bridge resolves that SteamID64 through `fragcity_user_links`, lists only non-cancelled services owned by the linked Paymenter user, and exposes only products assigned to the `FragCityCS2` server extension. Each returned service summary also includes the IDs of its own `ServiceUpgrade` records (`service_upgrade_ids`), allowing invoice upgrade lines to be matched to their parent service without guessing.

The server extension returns an allow-listed summary from the Pterodactyl Application API: service ID/status, server UUID/identifier/name, node ID, resource limits, dates, panel URL, panel username and email. Server ownership is verified by both the Pterodactyl `external_id` (Paymenter service ID) and Pterodactyl owner user ID before data is returned.

The inventory read also repairs a legacy Pterodactyl client identity when its email matches the linked Paymenter account and its `external_id` is empty or already matches that Paymenter user ID. It synchronizes the native Pterodactyl username, email, first/last name and `external_id`; a conflicting external ID or a username collision fails closed.

The `servers/password` endpoint accepts a customer-selected Pterodactyl password only after the signed request is validated and the service is confirmed to belong to the linked Paymenter user. The server extension verifies the Pterodactyl server owner and updates only that user's password through the Pterodactyl Application API. Pterodactyl hashes the password. The bridge stores only a `fragcity_panel_password_set_at` timestamp property; it never stores or returns plaintext or a password hash.

FragCity's website endpoint additionally requires an authenticated website session, CSRF token and successful re-entry of the current FragCity password. The website sends the new panel password to Paymenter only over the signed HTTPS bridge. Never expose the HMAC secret or Pterodactyl Application API key to browser JavaScript.

The panel password is intentionally independent from FragCity and Paymenter passwords. It cannot be read back after setting; customers can set a new one through FragCity at any time.

## Native Paymenter CS2 checkout

FragCity does **not** create Orders, Invoices, Services, Config Option rows or payment transactions through this API. It does not calculate or map product prices. Paymenter's native Product Checkout, Cart, Plan pricing, Config Options, Invoice lifecycle and server provisioning are the source of truth.

The website calls `POST /api/v1/fragcity/bridge/checkout-url` after confirming the customer is logged into FragCity. The bridge resolves the supplied SteamID64 to the linked Paymenter User, verifies the configured CS2 Product is enabled and uses `FragCityCS2`, and returns a one-time checkout URL. The URL contains an unpredictable 256-bit token, expires after two minutes and can be consumed once. The customer is signed into Paymenter and redirected to that Product's native `products.checkout` page.

After that redirect, Paymenter itself:
1. displays the Product's available Plans and attached native Config Options;
2. validates the customer selections and calculates the amount from the selected Plan and Config Option child prices;
3. creates the Order, Service, Service Properties and native Service Config records through its normal Cart checkout;
4. creates the Invoice and sends the customer to the selected Paymenter Gateway;
5. after the gateway verifies payment and records the successful invoice transaction, processes the paid invoice and dispatches the normal server CreateJob;
6. invokes `FragCityCS2`, which delegates Pterodactyl provisioning to Paymenter's inherited Pterodactyl implementation.

The signed FragCity endpoint accepts only the SteamID64 needed to start this hand-off. It never accepts browser-supplied prices, resource values, duration, Egg values, payment amounts or verified-payment claims.

### Native Product Config Options

Create these rows using **Paymenter Admin → Configuration → Config Options**, then attach them to the CS2 Product. They are ordinary Paymenter Config Options, not records created or synchronized by this API.

| Config Option | Parent Environment Variable | Suggested Type | Child Environment Variables |
| --- | --- | --- | --- |
| RAM | `memory` | Select or Slider | Exact MB values, e.g. `1024`, `1280`, `1536` |
| SSD Storage | `disk` | Select or Slider | Exact MB values, e.g. `5120`, `6144`, …, `10240` |
| CPU | `cpu` | Select or Slider | Exact percentages, e.g. `100`, `200`, `300`, `400` |
| Player Slots | `SRCDS_MAXPLAYERS` | Slider | One child per supported slot count from `5` through `64`; each child value is the exact slot count |
| Tickrate | `TICKRATE` | Select | `64`, `128` |

For every option, set each child Environment Variable to the exact value that should be stored. Paymenter uses the parent option's `env_variable` as the service property key and the selected child's `env_variable` as the value passed to the server extension.

Configure prices on each child for every recurring CS2 Plan:
- Base RAM and 5 Player Slots should have no surcharge where they are included in the base plan.
- Additional RAM and player capacity should carry the intended per-plan surcharge.
- CPU and SSD can remain zero-priced while they have no surcharge.
- 64 Tick is the base setting. Add a surcharge to 128 Tick only when that price is included in the Plan/Config Option quote.

Paymenter stores these choices as native `ServiceConfig` records. Its own `ExtensionHelper::getServiceProperties()` converts the stored values into `memory`, `disk`, `cpu`, `SRCDS_MAXPLAYERS` and `TICKRATE` properties before the Pterodactyl extension builds the Egg environment. Do not add a parallel resource map or Config Option lookup to FragCityAPI.

### Extension-defined CS2 Checkout fields

The FragCityCS2 server extension still supplies the smaller set of game-specific fields that are not represented as native Product Config Options in this slice: initial map, GameModeManager CFG, MAPGROUP, cooldown policy and Bot Guard settings. Their allowed values are validated by the FragCityCS2 extension before provisioning. Player Slots and Tickrate are intentionally absent from this custom Checkout manifest because they are managed by native Paymenter Config Options.

### ZarinPal Gateway

Enable **ZarinPal Gateway** under **Paymenter Admin → Extensions → Gateways** and configure:
- Merchant ID.
- The exact Paymenter Currency Code used by the CS2 Product Plans.
- Currency Unit: Toman (converted to Rial × 10) or Rial (no conversion).
- Sandbox mode only when using a ZarinPal sandbox merchant.

The gateway requests a ZarinPal authority for the Paymenter Invoice and verifies it server-to-server on callback before calling Paymenter's supported `ExtensionHelper::addPayment()` method. The browser redirect alone is never treated as payment proof. Paymenter then owns invoice settlement and server provisioning.

### SSO endpoint contract

Signed request:

```json
{
  "steamid64": "7656119XXXXXXXXXX"
}
```

Success response:

```json
{
  "success": true,
  "data": {
    "checkout_url": "https://paymenter.example/extensions/fragcity-api/checkout-login/64-character-one-time-token",
    "expires_in": 120
  }
}
```

The returned token is a bearer credential: keep it server-side until redirecting the same customer, never log it, never place it in analytics, and do not reuse it. The checkout-login route consumes the token atomically and immediately redirects to the configured Product's native Checkout page. The URL returned by Paymenter must remain on the configured Paymenter HTTPS origin.

## Installation

Copy this directory to:

```text
extensions/Others/FragCityAPI/
```

Then rebuild Composer's classmap and clear Laravel caches:

```bash
cd /var/www/paymenter
composer dump-autoload
php artisan optimize:clear
```

Enable **FragCity API** in Paymenter Admin → Extensions → Others and configure the secret. The extension migration runs when it is installed. Do not uninstall the extension after creating user links unless the mapping table has been backed up.

## Security notes

- HMAC message: `timestamp + newline + nonce + newline + raw request body`.
- Headers: `X-FragCity-Timestamp`, `X-FragCity-Nonce`, `X-FragCity-Signature`.
- Nonces are stored atomically in Laravel Cache for ten minutes to prevent replay.
- Request bodies and passwords are never written to logs.
- Core API keys and Pterodactyl credentials are not used by this bridge.
- The bridge creates no Orders, Invoices, Services, Config Options, Pterodactyl users or servers. Paymenter's native Checkout and server job own the order lifecycle; the FragCity CS2 server extension handles Pterodactyl client identity immediately before the official Paymenter server provisioner runs.

## Customer panel username

The `servers/username` endpoint updates the customer's Pterodactyl Client username for one owned CS2 service. The signed bridge resolves the SteamID64 to the linked Paymenter user, verifies service ownership, and delegates the operation to FragCityCS2. The website must authenticate the customer and protect the request with CSRF before sending it through the private HTTPS HMAC bridge.
